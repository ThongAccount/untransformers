# Milestone 0 — Reproducibility protocol

Every number this project reports must be reproducible from the repository alone
(plus a recorded environment manifest). This document pins what we pin, and is
honest about what the paper leaves unreconstructable.

## 1. What the paper pins vs what it leaves open

Pinned by the paper **[P]** (Table 1 + §6): u=5000, l=128, d=128, c=512, m=18,
batch 64, 60,000 batches, AdamW (γ=0.001, β1=0.9, β2=0.999), lr 0.001, dropout
0.1, PyTorch 2.0, RTX 4050 6 GB, weights N(0,0.01²)/biases zero, embedding ×√d,
HF BPE tokenizer at vocab 5000, 8.4M tokens, same-batches-same-order protocol.

Open in the paper **[U]**: the corpus book list ("top 100 books on English
children's literature"), the meaning of "top", text preprocessing, tokenizer
details beyond "HF BPE, vocab 5000", the RNG seed schedule, the AdamW weight
decay value, gradient clipping, per-position loss averaging granularity, whether
W^out was enabled (we decide: ON — HE_SPEC.md §5), and the epoch arithmetic
(§6 below).

## 2. Environment pinning (ledger D-08)

Recorded per run in `results/env_manifest.json`, generated by the runner:
python, torch, CUDA/cuDNN, GPU model, driver, `tokenizers` version, OS, and —
because our own ML practice has shown clock/power state changes kernel timing —
the GPU's sampled SM clock, power draw, and utilization during the run (per-step
nvidia-smi sampling). The paper's environment (RTX 4050 6 GB, PyTorch 2.0,
2023-era stack) is a recorded deviation; absolute latencies are NOT comparable
across hardware, only same-session arm-vs-arm comparisons are.

## 3. Data and tokenizer — the honest call (needs user sign-off)

**The paper's corpus cannot be exactly reconstructed.** "Top 100 books on English
children's literature available at gutenberg.org" **[P]** is not enumerable from
the paper: no book list, no ranking metric defining "top", no preprocessing
description, and no release (verified: no dataset/code linked from the arXiv
page, HF page, or GitHub search — negative result, not proof of nonexistence).

**Recommendation — Option A (same source, deterministic, pinned):** build our
corpus from Project Gutenberg itself, same as the paper did, but with a
selection rule we can freeze:

- Pool: Project Gutenberg's **"Children's Literature" reading list
  (`/ebooks/bookshelf/20`)**, optionally unioned with **"Children's Fiction"
  (`/ebooks/bookshelf/18`)** — both are hand-curated, enumerable lists with
  stable URLs (verified live). This matches the paper's stated source
  (gutenberg.org) and genre (English children's literature).
- Selection rule (deterministic): from the shelf listing, keep plain-text
  (UTF-8) English ebooks, sort by Gutenberg ebook ID ascending, take the first
  **100**. Snapshot the listing page + every book's plain text; record per-book
  Gutenberg ID + SHA-256 in `data/manifest.json` committed to the repo. Shelf
  membership drifts over time (volunteer-curated), so the manifest — not the
  live list — is the corpus.
- Preprocessing (our rule, logged as deviation D-01): strip the standard
  Gutenberg header/footer blocks (documented regex), normalize newlines, keep
  everything else. The paper does not describe preprocessing **[U]**.
- Expected deviation vs the paper: the book *set* will differ from the paper's
  (their "top" ranking is unpublished), so token distributions are not identical.
  Source, genre, scale target (~8.4M tokens), and format are matched. Report
  token count; do not claim an exact reproduction.

**Option B (rejected as primary):** a third-party packaged children's-books
corpus. Provenance and preprocessing unverifiable for our purposes, and our
search tooling was degraded this session (no reliable listing found) — any
candidate would need the same pinning discipline anyway. Acceptable only as a
cross-check corpus.

**Option C (impossible):** paper-exact reconstruction. Requires the paper's
unpublished book list and ranking.

**Decision needed from the user before Milestone 1** (Option A assumed in the
code; nothing trains until sign-off).

> **Decision (closed 2026-10-23, user-approved):** Option A. The snapshot is
> built and committed: bookshelf 20, all 317 ebook IDs sorted ascending by
> numeric ebook ID, first **100**; per-book SHA-256 for the raw download and
> the cleaned file; the shelf listing itself is hashed and snapshotted; the
> BPE tokenizer (vocab 5000) and the frozen 9,514,186-token array are
> committed with their SHA-256. See `docs/milestone-2/CORPUS.md` and
> `data/README.md`. Deviations D-01, D-19, D-20, D-21 are logged.

## 4. Tokenizer pinning

- HF `tokenizers` library, BPE, **vocab_size = 5000** **[P]**. Version recorded
  in the env manifest; the trained tokenizer JSON is committed with its SHA-256.
- Trained on the pinned corpus (Option A) with a recorded seed. Choices the
  paper does not specify **[U]**, ours and logged as deviation D-04:
  byte-level pre-tokenizer (GPT-2 style), no normalizer, `<|endoftext|>` as the
  sole special token.
- Because BPE training is deterministic given data + seed + library version, the
  token stream is reproducible from the manifest; a test (T15) asserts
  same-seed → identical token IDs and identical merges.

## 5. Training protocol pins

- From Table 1 **[P]**: batch 64 sequences × l=128 tokens; 60,000 batches;
  AdamW γ=0.001, β1=0.9, β2=0.999; dropout 0.1.
- Ours / recorded **[U]**: AdamW weight decay value and gradient clipping are
  not stated in the paper — we set weight decay 0.01 (AdamW's common default)
  and no clipping, both logged as deviations D-12/D-13 and held constant across
  arms (they cannot bias the arm comparison either way).
- **Same-batches-same-order** **[P]** ("not only all the batches ... are the
  same, but also the orders ... the same"): enforced structurally — batches are
  derived deterministically from a SHA-256-seeded `numpy.random.Generator` over
  the frozen token array, so both arms see identical batches in identical order
  by construction, not by replaying a log. The paper's "setting the random seed
  a couple of times" **[P]** is vague; ours is the precise schedule: seed once at
  data-pipeline start; arm init seeds are distinct but recorded (ledger D-14).
- Evaluation: paper reports **training cost only** (average training loss over a
  batch; "training cost equals perplexity in this task") **[P]**. We add a
  deterministic **held-out split** (last 5% of the token stream, never trained
  or used for selection) and report held-out loss/ppl separately — labeled a
  methodology improvement, not part of the paper's protocol (D-02).

## 6. Epoch-accounting caveat (ledger D-05)

The paper states 60,000 batches = **0.457 epochs** **[P]**. Under the standard
reading (60,000 × 64 sequences × 128 tokens = 491.5M tokens) the 8.4M-token
corpus implies ~58 epochs, not 0.457. The paper's number is consistent only with
counting 60,000 × 64 × **1 token** (3.84M ≈ 0.457 × 8.4M). **[U]** — unresolvable
from the paper. **Our protocol:** report *tokens processed* and *epochs of our
corpus* explicitly for every arm, and do not attempt to match "0.457 epochs"
literally. Training budget is compared in tokens, which is unambiguous.

## 7. Deviation ledger format

Append-only file `docs/milestone-0/DEVIATIONS.md`, one row per decision:

```
| ID | date | area (paper §) | paper says | we do | rationale | impact | status |
```

Status ∈ {open, accepted, user-approved}. Any result claim must cite the ledger
IDs it depends on. Seeded entries: D-01…D-14 as referenced in HE_SPEC.md §10 and
this document.

## 8. Gate-0 exit criteria (pipeline side)

1. Corpus manifest committed (book list + SHA-256 per book + total token count);
   corpus decision has user sign-off.
2. Tokenizer JSON + SHA committed; T15 passes.
3. Env manifest generator in place; a dry 50-step run of *either* arm produces
   identical batch streams across two invocations (byte-identical token tensors).
4. DEVIATIONS.md seeded with all §§1–7 entries.
5. Still no training for results and no interpretation of any run (gate 0).
